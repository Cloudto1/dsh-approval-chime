## 8. `dsh plugin …` CLI 语义实测（README §5 更正依据）

任务要求先独立确认该子命令是否真实存在及其语义。结论：**存在，但它不是「安装插件」的完整步骤**。

实测源码 `<dsh-install>\node_modules\@deepseek-ai\dsh\lib\plugin-Ddi42qoW.js`：

```js
// 文档注释原文：
// `dsh plugin --profile <name> <args...>` — profile plugin management as a
// thin pnpm forwarder: initialize the profile on first use, run
// `pnpm <args...>` in the profile directory, then reconcile the
// `dsh.profile.bundles` layer list against the installed state …
const result = spawnSync("pnpm", args.map(...), { cwd: dir, stdio: "inherit", shell: process.platform === "win32" });
…
if (exitCode === 0) reconcilePlugins(before, dir);
```

* `dsh plugin --profile web <args…>` = **把参数原样转发给 profile 目录里的 `pnpm`**；成功后按「已安装依赖」重算 `dsh.profile.bundles`（`exportsPatch()` 用 `resolveBundleDir` 判断某依赖是否声明 `dsh.bundle.patch`，是且不在 bundles 里就追加）。
* `dsh --help` 的示例也是 `dsh plugin --profile tui add <package>`。
* 因此 **`dsh plugin --profile web install` 只是 `pnpm install`**：它本身**不会新增依赖**；只有当 `package.json` 已声明我们的 `link:` 依赖时，才会顺手建 junction（并把缺失的 bundles 项补上）。README §5 原文把它放在「步骤 1 已手改 package.json」之后，语义上勉强成立，但**作为「挂载步骤」的表述不准确**，已在 README 里更正并加了警示块。
* 能一条命令完成三件事的正确形式是：`dsh plugin --profile web add "link:D:/…/dsh-approval-chime"`。**本任务没有采用**：它会跑 pnpm、改写 `pnpm-lock.yaml` 并重排 `node_modules`（对正在运行的宿主来说副作用大于收益），而等价的手工/脚本三处改动风险更小、可逐字节复核。

## 9. 已知行为与限制（用户须知；均不构成验收失败）

| # | 事项 | 说明与应对 |
| --- | --- | --- |
| F1 | **非 loopback 页面分区页渲染为空（导航行仍在）** | 平台在非 loopback 下 `persistence='memory'`，命名空间拿不到 `status==='ready'` → 分区组件返回 `null`（不会有"内存保留"提示行）。rev-7 起该槽是插件自己的 `settings.section`，所以导航行照常出现、只是页面为空。**验收必须用 `http://127.0.0.1:3080`。**（t4 评审探针 B 实测；本仓 probe-3 §c 同样证明 `status!=='ready'` ⇒ 渲染 `null`） |
| F2 | **一次鼠标拖拽可能写两次同一个值** | 释放时 `pointerup` 与 `mouseup` 都会提交，而草稿要等写成功才清空，故同一 `set('volume', same)` 可能出现两次。平台写队列串行化并携带 `pendingRevision`（`client-ui-settings` 的 `mutate()`），被 revision 栅栏拒绝也只是 `recover()` 后正常 resolve，故语义等价于一次、不会弹错。（probe-3 实测记录 `[{volume,60},{volume,60}]`；probe-5 C.4d–f 为平台侧证据） |
| F3 | **`uiSession` 是硬 inject** | 浏览器半 `inject=['slots','locale','settingsScope','uiSession']`：任一服务缺失，cordis 不会 apply，**提示音与分区页会一起不挂载**。当前目标 profile 不会触发：`dsh-web-app` 已挂 4 个 provider（`ui-session`/`ui-renderer`/`dsh-client-locale`/`ui-settings` 各自提供），且内置 `ui-approval` 同样 `inject` `uiSession`（probe-5 H7/H7f/H7g 有 `file:line`）。适用边界：仅在宿主改名/移除某服务时才会出现"整体不挂载"。 |
| F4 | **未获得用户手势时，被自动播放策略拦下的那一次会"迟到"响** | probe-6 实测：锁定状态下提示音**不是被丢弃，而是已建图并排期**（振荡器 `start()` 在冻结的 `currentTime`），解锁路径只 `resume()`、不重建；因此首次成功 resume 时那次声音会被听到。计数语义：该次同时 `triggers +1` 与 `suppressedPolicy +1`（分区页同时显示"已触发"和"被浏览器自动播放策略拦下 ×1"）。**应对：重启后如果第一次没听见，先点一下页面或点「试听」解锁音频。** |
| R1 | 去重表上限 256（t3 登记） | 被淘汰的 key 若仍在某次快照里，理论上会再响一次；UI 会话里不可达。 |
| R2 | 同一次快照里的多个新审批只响一次（t3 登记） | 实现明示的批处理；验收只要求「同一次审批只响一次」。 |
| R3 | H3 遮蔽属宿主限制（t3 登记） | 每个 session 只暴露一个 pending（按 precedence 取大者），同会话并发提问+审批时审批可能被遮蔽而漏响。 |
| R4 | `dsh plugin --profile web install` 不是挂载步骤 | 见 §8；README 已更正。 |
